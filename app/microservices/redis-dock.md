# Redis — техническая документация файлового хранилища

**Проект:** File Storage  
**Компонент:** Redis  
**Назначение:** Ограничение запросов, контроль доступа, защита от злоупотреблений, временное хранение данных и координация процессов.

---

# 1. Назначение Redis

Redis используется как быстрое временное хранилище данных, необходимых для управления работой приложения.

Redis не должен заменять PostgreSQL в качестве основной базы данных.

Основные задачи:

1. Ограничение частоты запросов (Rate Limiting).
2. Ограничение количества создаваемых объектов.
3. Ограничение количества операций пользователя.
4. Контроль временных блокировок.
5. Защита от перебора паролей и токенов.
6. Хранение временных состояний.
7. Контроль параллельных операций.
8. Кэширование часто запрашиваемых данных.
9. Координация фоновых задач.
10. Временное хранение одноразовых кодов и токенов.

## 1.1. Принцип работы

Redis является дополнительным инфраструктурным слоем.

Основная архитектура:

    FastAPI
       |
       v
    Services
       |
       +------ Redis
       |
       +------ PostgreSQL
       |
       +------ MinIO

PostgreSQL отвечает за постоянное хранение данных.

Redis отвечает за временные данные, быстрые проверки и координацию.

MinIO отвечает за хранение файлов.

# 2. Rate Limiting — ограничение частоты запросов

Rate Limiting позволяет ограничивать количество запросов за определённый промежуток времени.

Применяется для:

- Защиты API от чрезмерной нагрузки.
- Предотвращения автоматизированного злоупотребления.
- Ограничения частоты загрузок и скачиваний.
- Защиты авторизации.
- Контроля использования ресурсов пользователями.

## 2.1. Типы ограничений

### По IP-адресу

Ограничивает количество запросов с одного IP.

Пример:

    100 запросов за 60 секунд

Ключ Redis:

    rate_limit:ip:{ip_address}

### По пользователю

Ограничивает количество запросов конкретного пользователя.

Пример:

    200 запросов за 60 секунд

Ключ Redis:

    rate_limit:user:{user_id}

### По типу операции

Позволяет устанавливать отдельные ограничения для разных действий.

Примеры:

    rate_limit:upload:{user_id}
    rate_limit:download:{user_id}
    rate_limit:delete:{user_id}

### По API endpoint

Позволяет ограничивать конкретные маршруты.

Примеры:

    rate_limit:login:{ip}
    rate_limit:register:{ip}
    rate_limit:password_reset:{ip}

## 2.2. Алгоритмы Rate Limiting

Поддерживаемые алгоритмы:

**Fixed Window**

Подсчитывает количество запросов в фиксированном временном интервале.

Пример:

- Максимум 100 запросов.
- Окно 60 секунд.
- После завершения окна счётчик сбрасывается.

Преимущества:
- Простота реализации.
- Небольшое потребление памяти.

Недостаток:
- Возможен резкий всплеск запросов на границе двух окон.

**Sliding Window**

Учитывает запросы за последние N секунд относительно текущего момента.

Преимущества:
- Более равномерное ограничение.
- Нет выраженного эффекта границы окон.

Недостатки:
- Более сложная реализация.
- При использовании Redis Sorted Sets требуется управление количеством записей.

**Token Bucket**

Пользователь получает ограниченный запас условных токенов.

Каждый запрос расходует один или несколько токенов. Токены постепенно восстанавливаются.

Преимущества:
- Позволяет кратковременные всплески нагрузки.
- Подходит для API с разными типами операций.

Рекомендуемый выбор:

- Для обычных API — Fixed Window или Sliding Window.
- Для загрузок и скачиваний — Token Bucket либо отдельные ограничения по объёму.
- Для авторизации — Sliding Window с дополнительной блокировкой.

## 2.3. Пример конфигурации

| Операция | Ограничение |
|---|---:|
| Обычные API-запросы | 120 / мин |
| Авторизация | 5 / мин |
| Регистрация | 3 / час |
| Создание бакетов | 10 / час |
| Удаление объектов | 60 / мин |
| Создание объектов | 30 / мин |
| Запросы скачивания | 120 / мин |

Это стартовые значения для тестирования, а не универсальные безопасные лимиты. В дальнейшем их следует вынести в конфигурацию и адаптировать к тарифам и нагрузке.

# 3. Ограничение создания ресурсов

Redis позволяет быстро проверять, сколько ресурсов пользователь уже создал или создал за определённое время.

## 3.1. Ограничение количества бакетов

Пример:

    Максимум 20 бакетов на пользователя.

Ключ:

    limits:buckets:{user_id}

При создании бакета:

1. Получить текущее количество бакетов.
2. Проверить лимит.
3. Если лимит достигнут — отклонить создание.
4. Если лимит не достигнут — создать бакет.
5. Обновить счётчик.

Важно: Redis-счётчик не должен быть единственным источником истины для постоянного количества бакетов.

При сбросе Redis или ошибке синхронизации счётчик может потерять точность. Для строгого ограничения необходимо сверяться с PostgreSQL либо использовать надёжную синхронизацию.

## 3.2. Ограничение количества объектов

Пример:

    Максимум 10 000 объектов на пользователя.

Ключ:

    limits:objects:{user_id}

Используется для контроля количества файлов в хранилище.

## 3.3. Ограничение объёма хранилища

Пример:

    Пользователь имеет квоту 10 GB.

Ключ:

    usage:storage:{user_id}

При загрузке:

1. Получить текущий использованный объём.
2. Получить размер нового файла.
3. Проверить доступную квоту.
4. Зарезервировать место.
5. Выполнить загрузку.
6. Подтвердить изменение занятого объёма.
7. При неудаче освободить резерв.

Для этого нужна атомарная операция резервирования.

Нельзя делать простую последовательность GET → проверка → SET: параллельные загрузки могут одновременно пройти проверку и превысить квоту.

Для надёжного учёта следует использовать атомарный Lua-скрипт или транзакционный механизм с контролем версии данных.

Окончательный учёт занятого места необходимо сверять с PostgreSQL и MinIO.

# 4. Контроль доступа и временные блокировки

Redis может хранить временные ограничения доступа.

## 4.1. Блокировка пользователя

Применяется при:

- Подозрительной активности.
- Многократных неудачных попытках авторизации.
- Превышении ограничений.
- Обнаружении автоматизированных запросов.

Ключ:

    security:blocked:user:{user_id}

Значение:

    1

TTL:

    900 секунд

При каждом запросе:

1. Проверить наличие блокировки.
2. Если ключ существует — запретить операцию.
3. Если отсутствует — продолжить обработку.

Постоянные блокировки должны храниться в PostgreSQL, Redis используется для временных.

## 4.2. Блокировка IP

Ключ:

    security:blocked:ip:{ip_address}

Используется для временного ограничения подозрительных IP.

Не следует считать IP надёжным идентификатором пользователя: за одним IP могут находиться сотни пользователей.

## 4.3. Защита от перебора паролей

Ключ:

    security:login_attempts:{ip_address}

Дополнительный ключ:

    security:login_attempts:user:{user_id}

Логика:

1. Зафиксировать неудачную попытку.
2. Увеличить счётчик.
3. Проверить количество попыток.
4. При превышении лимита применить временную задержку или блокировку.
5. После истечения TTL счётчик автоматически удалится.

Необходимо учитывать, что злоумышленник может распределять запросы между разными IP.

# 5. Контроль параллельных операций

Redis позволяет ограничивать количество одновременно выполняемых операций.

Примеры:

- Максимум 3 одновременные загрузки на пользователя.
- Максимум 5 одновременных скачиваний.
- Максимум 2 операции удаления.
- Ограничение параллельной обработки архивов.

Ключ:

    concurrency:upload:{user_id}

Возможная реализация:

- Redis Semaphore.
- Атомарный Lua-скрипт.
- Redis Sorted Set с идентификаторами операций и временем аренды.

Важно предусмотреть TTL, освобождение ресурсов и восстановление после падения приложения. Обычный INCR/DECR без контроля срока жизни может привести к зависшим счётчикам.

---

# 6. Временные токены и состояния

Redis подходит для хранения данных с ограниченным сроком действия.

## 6.1. Одноразовые токены

Примеры:

- Подтверждение электронной почты.
- Сброс пароля.
- Подтверждение критической операции.
- Одноразовая ссылка доступа.

Ключ:

    tokens:reset_password:{token_hash}

TTL:

    600 секунд

Рекомендуется хранить хеш токена, а не исходный секрет.

Одноразовое использование должно выполняться атомарно: проверка и удаление токена не должны разделяться на независимые операции.

## 6.2. Временные состояния операций

Пример:

    operations:upload:{operation_id}

Возможные состояния:

- PENDING
- PROCESSING
- COMPLETED
- FAILED
- CANCELLED

Это позволяет отслеживать длительные операции и восстанавливать их состояние после ошибок.

Если состояние критично для целостности данных, его необходимо сохранять и в постоянном хранилище.

# 7. Кэширование

Redis можно использовать для кэширования часто запрашиваемой информации.

Возможные данные:

- Информация о пользователе.
- Метаданные бакетов.
- Информация о квотах.
- Статистика использования.
- Списки объектов.
- Настройки пользователя.

Примеры ключей:

    cache:user:{user_id}
    cache:bucket:{bucket_id}
    cache:storage_stats:{user_id}

Для каждого типа кэша необходимо определить TTL и механизм инвалидации.

При изменении данных следует удалять или обновлять соответствующий кэш.

Не рекомендуется кэшировать результаты проверки прав доступа надолго: после отзыва разрешения старые права могут продолжать действовать до истечения TTL.

# 8. Redis для аналитики и безопасности

Redis может использоваться для быстрой обработки временных счётчиков.

Примеры:

- Количество загрузок за минуту.
- Количество ошибок авторизации.
- Число запросов с IP.
- Частота удаления объектов.
- Количество операций пользователя.

Примеры ключей:

    analytics:uploads:{user_id}
    analytics:downloads:{user_id}
    analytics:errors:{ip_address}

Для временной аналитики можно применять:

- INCR — увеличение счётчика.
- EXPIRE — установка срока действия.
- ZADD — добавление событий в отсортированное множество.
- ZCOUNT — подсчёт элементов за временной диапазон.
- HINCRBY — увеличение поля в Hash.

При этом Redis не заменяет таблицу Events в PostgreSQL. Историческая аналитика должна строиться по постоянным событиям.

---

# 9. Структура ключей Redis

Рекомендуется единый формат:

    {namespace}:{entity}:{identifier}:{metric}

Примеры:

    rate_limit:user:123
    rate_limit:ip:127.0.0.1
    security:blocked:user:123
    security:login_attempts:127.0.0.1
    limits:buckets:123
    limits:objects:123
    usage:storage:123
    concurrency:upload:123
    cache:user:123

Требования:

1. Использовать понятные namespace.
2. Не хранить секреты в именах ключей.
3. Устанавливать TTL для временных данных.
4. Не допускать бесконтрольного роста количества ключей.
5. Использовать единый формат идентификаторов.

# 10. Интеграция с FastAPI

Рекомендуемая структура:

    app/
    ├── core/
    │   └── redis.py
    ├── services/
    │   ├── event_service.py
    │   ├── analytics_service.py
    │   ├── rate_limit_service.py
    │   ├── quota_service.py
    │   └── security_service.py
    ├── dependencies/
    │   └── redis.py
    └── api/
        └── ...

## 10.1. Redis Client

Создаётся один асинхронный Redis-клиент на процесс приложения.

Не нужно создавать новое соединение для каждого HTTP-запроса.

При запуске приложения клиент инициализируется, при завершении — закрывается.

## 10.2. RateLimitService

Ответственность:

- Проверка лимитов.
- Увеличение счётчиков.
- Вычисление оставшегося количества запросов.
- Определение времени до сброса.
- Возврат результата проверки.

## 10.3. QuotaService

Ответственность:

- Проверка квот.
- Резервирование места.
- Подтверждение загрузки.
- Освобождение резерва.
- Контроль количества объектов.

## 10.4. SecurityService

Ответственность:

- Проверка временных блокировок.
- Учёт ошибок авторизации.
- Создание временных ограничений.
- Проверка подозрительной активности.

# 11. Ошибки и отказ Redis

Необходимо заранее определить поведение приложения при недоступности Redis.

Варианты:

**Fail-open**

Приложение продолжает работу без ограничения.

Подходит для некритичного кэширования, но опасен для защиты от злоупотреблений.

**Fail-closed**

Операция запрещается, если Redis недоступен.

Подходит для критических ограничений, если обход лимита недопустим.

Рекомендуемая политика:

| Механизм | Поведение при недоступности |
|---|---|
| Кэширование | Продолжать без кэша |
| Rate Limiting API | По политике риска; для чувствительных endpoint — fail-closed |
| Ограничение авторизации | Fail-closed или отдельный резервный механизм |
| Квоты хранилища | Проверять через PostgreSQL, не разрешать загрузку без надёжной проверки |
| Временные блокировки | Не обходить критические блокировки |
| Временные состояния | Восстанавливать из постоянного хранилища, если они критичны |

Ошибки Redis должны логироваться, но нельзя записывать в логи пароли, токены и другие секреты.

# 12. Безопасность Redis

Обязательные требования:

1. Не публиковать Redis-порт в интернет.
2. Использовать отдельную внутреннюю Docker-сеть.
3. Настроить пароль или ACL.
4. Использовать TLS при необходимости сетевого подключения между узлами.
5. Ограничить доступ приложений к Redis.
6. Не хранить пароли и JWT в открытом виде.
7. Настроить лимит памяти.
8. Выбрать подходящую политику eviction.
9. Контролировать количество соединений.
10. Не разрешать пользовательскому API произвольное выполнение Redis-команд.

Для временных ключей можно использовать TTL, а для кэша — отдельную политику вытеснения.

Если Redis хранит важные для безопасности счётчики или резервы, нельзя допускать их случайного удаления из-за eviction. Желательно разделить кэш и критичные данные по разным Redis-инстансам либо использовать отдельные политики и хранилища.

# 14. Критерии готовности

Redis-интеграция считается реализованной, если:

- Все временные ключи имеют контролируемый срок жизни.
- Rate Limiting работает атомарно.
- Ограничения не обходятся параллельными запросами.
- Квоты не позволяют превысить доступный объём хранилища.
- Временные блокировки корректно истекают.
- Ошибки Redis не приводят к неконтролируемому обходу критических ограничений.
- Redis не является единственным источником постоянных данных.
- Секреты и персональные данные не раскрываются через ключи и логи.
- Есть мониторинг памяти, соединений и ошибок.

**Главный принцип:** Redis управляет временными ограничениями и быстрыми проверками, PostgreSQL хранит постоянные данные и обеспечивает долговременную целостность, MinIO хранит файлы.
