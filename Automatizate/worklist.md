# Техническое задание
# Storage Analytics — система сбора и анализа активности файлового хранилища

**Версия:** 1.0  
**Статус:** В разработке  
**Назначение:** Создание самостоятельной подсистемы аудита, аналитики и обнаружения подозрительной активности.

---

# 1. Цель проекта

Разработать систему, которая собирает информацию о действиях пользователей в файловом хранилище, сохраняет события и анализирует их.

Система должна не просто хранить историю операций, а уметь отвечать на вопросы:

- Кто и когда загружал или скачивал файлы?
- Какие пользователи наиболее активны?
- Какие бакеты используются чаще всего?
- Сколько данных загружается и скачивается?
- Есть ли подозрительная активность?
- Происходят ли массовые операции?
- Есть ли необычные изменения поведения пользователей?
- Какие события требуют внимания администратора?

**Важно:** система аналитики не должна повторно реализовывать загрузку, скачивание, удаление файлов, авторизацию или управление бакетами. Она получает информацию о происходящих операциях из уже существующего приложения.

# 2. Архитектура

Используем архитектуру:

API → Service → Repository → PostgreSQL

Дополнительно выделяем аналитические компоненты:

- Event Collector — получение и регистрация событий.
- Event Repository — взаимодействие с таблицей событий.
- Event Service — управление событиями и подготовка данных.
- Analytics Service — выполнение аналитических запросов и формирование результатов.
- Analyzers — алгоритмы анализа данных.
- Workers — фоновые задачи, которые в перспективе будут запускать анализ независимо от HTTP-запросов.

На первом этапе это единое приложение (модульный монолит). Не нужно создавать отдельные микросервисы.

# 4. Модель Event

Основная сущность системы — событие.

Каждая запись представляет собой отдельный факт о произошедшей операции.

Уже предусмотренные поля:

| Поле | Назначение |
|---|---|
| `id` | Уникальный идентификатор |
| `created_at` | Время события |
| `user_id` | Пользователь, если известен |
| `IP` | IP-адрес источника |
| `bucket_name` | Название бакета |
| `bucket_type` | Тип бакета |
| `event_type` | Тип операции |
| `status` | Результат операции |
| `object_name` | Имя объекта |
| `file_size` | Размер файла |

`id` и `created_at` уже наследуются от Base.

В перспективе рекомендуется добавить:

| Поле | Назначение |
|---|---|
| `request_id` | Связь события с HTTP-запросом |
| `source` | Источник события: API или MinIO |
| `actor_type` | Тип субъекта: пользователь, анонимный клиент, система |
| `duration_ms` | Длительность операции |
| `error_code` | Код ошибки при неудачной операции |

Не нужно добавлять все поля сразу. Сначала реализуй аналитику на существующей модели.

## 4.1. Типы событий

На первом этапе:

- UPLOAD — загрузка файла.
- DOWNLOAD — скачивание файла.
- DELETE — удаление файла.

В будущем можно добавить:

- CREATE_BUCKET;
- DELETE_BUCKET;
- LOGIN;
- LOGOUT;
- ACCESS_DENIED;
- AUTH_FAILED.

## 4.2. Статусы событий

- SUCCESS — операция выполнена.
- FAILED — операция завершилась ошибкой.
- DENIED — операция запрещена системой.

События должны сохраняться как отдельные записи. Не изменять старые события при появлении новых операций.

# 5. Event Repository

**Назначение:** исключительно взаимодействие с базой данных.

Repository не должен принимать бизнес-решения, проверять права пользователей или самостоятельно определять подозрительную активность.

## 5.1. Обязательные функции

### `create_event(event)`

Создание новой записи события.

Зачем:
- Сохранить информацию об операции.
- Обеспечить доступность события для дальнейшего анализа.

### `get_user_events(user_id, limit)`

Получение событий определённого пользователя.

Зачем:
- Просмотр истории действий.
- Анализ активности пользователя.

### `get_bucket_events(bucket_name, limit)`

Получение событий конкретного бакета.

Зачем:
- Анализ использования бакета.
- Поиск операций с определёнными файлами.

### `get_events_by_type(event_type, limit)`

Получение событий определённого типа.

Зачем:
- Отдельный анализ загрузок, скачиваний и удалений.

### `get_events_by_period(start_date, end_date)`

Получение событий за временной промежуток.

Зачем:
- Построение статистики за день, неделю или месяц.

### `get_recent_events(limit)`

Получение последних событий системы.

Зачем:
- Панель мониторинга.
- Просмотр последних операций администраторами.

## 5.2. Функции агрегации

Агрегацию желательно выполнять средствами SQL, а не загружать все записи в Python.

### `count_events_by_type(start_date, end_date)`

Количество событий каждого типа.

### `count_events_by_status(start_date, end_date)`

Количество успешных, неудачных и запрещённых операций.

### `get_total_uploaded_size(start_date, end_date)`

Суммарный размер успешно загруженных файлов.

### `get_total_downloaded_size(start_date, end_date)`

Суммарный размер успешно скачанных файлов.

### `get_top_active_users(start_date, end_date, limit)`

Пользователи с наибольшим количеством событий.

### `get_top_active_buckets(start_date, end_date, limit)`

Бакеты с наибольшим количеством операций.

# 6. Event Service

**Назначение:** управление событиями и подготовка данных для других компонентов.

Здесь не должно быть SQL-запросов напрямую. Для доступа к данным используется Repository.

## Обязательные функции

### `create_event(...)`

Принимает данные о совершённой операции и организует сохранение события.

### `get_user_activity(user_id, limit)`

Получает историю действий пользователя.

Дополнительные правила:
- Проверка допустимого значения limit.
- Возврат событий в порядке убывания даты.
- Обработка пустого результата.

### `get_bucket_activity(bucket_name, limit)`

Получает историю действий с бакетом.

### `get_recent_activity(limit)`

Получает последние события системы.

### `get_events_by_period(start_date, end_date)`

Получает события за выбранный промежуток времени.

### `get_activity_by_type(event_type, start_date, end_date)`

Получает события конкретного типа за период.

**Результат этапа:** EventService предоставляет удобные методы для работы с историей событий. Он не занимается сложными алгоритмами обнаружения аномалий.

# 7. Analytics Service

**Назначение:** формирование аналитических данных из событий.

Этот компонент объединяет результаты Repository и передаёт их анализаторам.

## 7.1. Общая статистика

### `get_general_statistics(start_date, end_date)`

Возвращает:
- Общее количество событий.
- Количество загрузок.
- Количество скачиваний.
- Количество удалений.
- Количество успешных операций.
- Количество ошибок.
- Количество запрещённых операций.

### `get_storage_statistics(start_date, end_date)`

Возвращает:
- Общий объём загруженных данных.
- Общий объём скачанных данных.
- Количество загруженных объектов.
- Количество удалений.
- Распределение операций по бакетам.

Важно: это статистика по событиям, а не гарантированно актуальный размер файлового хранилища. Для точного текущего объёма потребуется получать данные непосредственно из MinIO или отдельного учёта объектов.

### `get_user_statistics(user_id, start_date, end_date)`

Возвращает:
- Количество операций пользователя.
- Количество загрузок.
- Количество скачиваний.
- Количество удалений.
- Объём загруженных и скачанных данных.
- Количество неудачных операций.

### `get_bucket_statistics(bucket_name, start_date, end_date)`

Возвращает статистику использования конкретного бакета.

### `get_activity_timeline(start_date, end_date, interval)`

Формирует временную последовательность активности.

Например:
- Количество операций за каждый час.
- Количество операций за каждый день.
- Количество операций за каждую неделю.

Эти данные в дальнейшем можно использовать для графиков.

# 8. Analyzers — аналитические алгоритмы

Это наиболее важная часть проекта.

Анализаторы не должны заниматься HTTP-запросами и напрямую управлять базой данных. Они получают необходимые данные и возвращают результаты анализа.

# 8.1. Activity Analyzer

**Назначение:** анализ общей активности пользователей.

### `calculate_user_activity(events)`

Определяет количество операций каждого пользователя.

### `find_most_active_users(events, limit)`

Находит наиболее активных пользователей.

### `calculate_user_activity_change(current_period, previous_period)`

Сравнивает активность пользователя за два периода.

Пример:

- На прошлой неделе пользователь совершил 50 операций.
- На текущей неделе — 250 операций.
- Активность увеличилась на 400%.

Это не обязательно подозрительная активность, но повод для дополнительного анализа.

# 8.2. Traffic Analyzer

**Назначение:** анализ сетевой и операционной активности.

### `calculate_ip_activity(events)`

Определяет количество операций с каждого IP-адреса.

### `find_high_frequency_ips(events, threshold)`

Находит IP-адреса с чрезмерно высокой частотой запросов.

### `find_failed_request_spikes(events, threshold)`

Ищет резкие увеличения количества неудачных операций.

### `find_multiple_users_from_ip(events)`

Определяет IP-адреса, с которых работают несколько аккаунтов.

Важно: несколько пользователей с одного IP не обязательно означают нарушение. Это может быть общий интернет, NAT или корпоративная сеть.

# 8.3. Storage Analyzer

**Назначение:** анализ использования файлового хранилища.

### `calculate_upload_download_ratio(events)`

Рассчитывает соотношение загрузок и скачиваний.

### `find_mass_uploads(events, threshold)`

Ищет массовые загрузки файлов.

### `find_mass_downloads(events, threshold)`

Ищет массовые скачивания файлов.

### `find_mass_deletions(events, threshold)`

Ищет массовые удаления объектов.

### `find_unusual_bucket_activity(events)`

Ищет необычные изменения активности в отдельных бакетах.

# 8.4. Security Analyzer

**Назначение:** обнаружение потенциально подозрительного поведения.

### `detect_brute_force(events, threshold, time_window)`

Ищет большое количество неудачных попыток доступа за короткое время.

### `detect_unusual_user_activity(events, baseline)`

Сравнивает текущую активность пользователя с его обычным поведением.

### `detect_mass_data_exfiltration(events, threshold)`

Ищет признаки массового скачивания данных.

### `detect_suspicious_ip_activity(events, threshold)`

Ищет IP-адреса с подозрительными комбинациями событий.

### `detect_unusual_access_patterns(events)`

Ищет необычные последовательности действий.

Пример:
- Пользователь обычно скачивает 2–5 файлов в день.
- Внезапно скачивает 300 файлов за несколько минут.

Это повод сформировать предупреждение, но не доказательство атаки.

# 9. Security Alerts — система предупреждений

**Назначение:** сохранять результаты обнаружения подозрительной активности.

Предупреждения должны храниться отдельно от обычных событий.

Предлагаемая модель `SecurityAlert`:

| Поле | Назначение |
|---|---|
| `id` | Идентификатор предупреждения |
| `created_at` | Время обнаружения |
| `user_id` | Связанный пользователь, если известен |
| `event_id` | Связанное событие, если есть |
| `alert_type` | Тип предупреждения |
| `severity` | Уровень важности |
| `description` | Описание причины |
| `status` | Состояние предупреждения |

Уровни важности:

- LOW — низкий.
- MEDIUM — средний.
- HIGH — высокий.
- CRITICAL — критический.

Состояния:

- NEW — новое.
- REVIEWED — просмотрено.
- RESOLVED — обработано.
- FALSE_POSITIVE — ложное срабатывание.

## 9.1. Alert Repository

### `create_alert(alert)`

Сохранение предупреждения.

### `get_alerts(limit, severity, status)`

Получение списка предупреждений с фильтрацией.

### `get_user_alerts(user_id, limit)`

Получение предупреждений конкретного пользователя.

### `update_alert_status(alert_id, status)`

Изменение статуса предупреждения.

## 9.2. Alert Service

### `create_alert(...)`

Создаёт предупреждение на основании результата анализа.

### `get_alerts(...)`

Возвращает предупреждения с необходимыми фильтрами.

### `resolve_alert(alert_id)`

Помечает предупреждение как обработанное.

### `mark_false_positive(alert_id)`

Помечает предупреждение как ложное срабатывание.

# 11. Workers — фоновая обработка

На начальном этапе анализ можно запускать вручную или через API для тестирования.

В дальнейшем потребуется отдельный фоновый процесс.

Предлагаемая функция:

### `run_analytics_cycle()`

Один полный цикл анализа:

1. Получает события за выбранный период.
2. Передаёт их анализаторам.
3. Получает результаты.
4. Формирует предупреждения.
5. Сохраняет результаты.
6. Завершает цикл.

Важно предусмотреть защиту от повторного создания одинаковых предупреждений при каждом запуске анализа.

В будущем можно добавить:
- Периодический запуск.
- Обработку новых событий.
- Очередь задач.
- Повторные попытки при ошибках.
- Логирование выполнения.

# 12. Надёжность и безопасность

Обязательные требования:

1. Не сохранять JWT, пароли, Authorization-заголовки и секреты presigned URL.
2. Не считать IP-адрес идентификатором пользователя.
3. Не удалять историю событий при удалении пользователя.
4. Сохранять временные метки с часовым поясом.
5. Использовать ограничения на размер выдачи.
6. Проверять корректность временных диапазонов.
7. Не разрешать обычным пользователям просматривать чужую историю.
8. Не допускать бесконечной загрузки событий в память.
9. Предусмотреть индексы для часто используемых фильтров: `user_id`, `created_at`, `event_type`, `IP`, `bucket_name`.
10. Разделять аудит событий и технические логи приложения.

Отдельный момент: PostgreSQL и MinIO не имеют общей транзакции. Если операция в MinIO прошла успешно, а запись события в PostgreSQL завершилась ошибкой, событие может потеряться. В дальнейшем следует изучить Transactional Outbox или другой механизм надёжной доставки событий.

Также нужно учитывать, что при прямой загрузке или скачивании через presigned URL FastAPI не всегда видит сам факт успешной передачи файла. Для этого в перспективе понадобится интеграция с аудитом MinIO.

# 14. Требования к качеству кода

Во время разработки придерживаться следующих правил:

- Использовать асинхронный SQLAlchemy.
- Использовать типизацию аргументов и возвращаемых значений.
- Разделять Repository, Service и Analyzer.
- Не смешивать SQL-запросы с бизнес-логикой.
- Не размещать бизнес-логику в API-маршрутах.
- Не создавать дублирующие методы без необходимости.
- Использовать понятные названия функций и переменных.
- Обрабатывать исключения там, где это действительно необходимо.
- Не скрывать ошибки пустым `except`.
- Писать тесты для критически важных алгоритмов.
- Проверять граничные значения и пустые результаты.

# 16. Правила нашей совместной разработки

Разработка ведётся последовательно, этап за этапом.

**Роль разработчика:** самостоятельно писать код, принимать архитектурные решения и объяснять назначение реализуемых функций.

**Роль технического руководителя:** проверять код, указывать на ошибки, объяснять архитектурные проблемы, предлагать улучшения и давать следующие задачи.

При проверке каждой функции оцениваются:

1. Корректность логики.
2. Правильность работы с SQLAlchemy.
3. Архитектурное расположение функции.
4. Типизация и обработка ошибок.
5. Производительность.
6. Возможность дальнейшего расширения.

Готовый код не предоставляется заранее без запроса разработчика. При обнаружении ошибки сначала объясняется проблема, после чего разработчик получает возможность исправить её самостоятельно.

**Главный принцип:** разработчик должен понимать не только то, как написать функцию, но и зачем она нужна системе, какие данные принимает, что возвращает и какие последствия имеет её выполнение.
