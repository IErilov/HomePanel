
# Основы архитектуры проекта

## 1. Общая идея

Архитектура нужна для разделения ответственности между частями приложения.

Каждая директория отвечает за определённую задачу:

| Директория | Назначение |
|---|---|
| `core/` | Основные механизмы и настройки приложения |
| `models/` | Структура данных и ORM-модели |
| `repo/` | Работа с базой данных |
| `services/` | Бизнес-логика приложения |

Главный принцип: не смешивать разные виды ответственности в одном месте.

---

## 2. Core — ядро приложения

`core/` содержит общие механизмы, необходимые всему приложению.

Примеры:
- `config.py` — настройки приложения.
- `database.py` — подключение к базе данных.
- `security.py` — механизмы безопасности.
- `logging.py` — настройка логирования.
- `exceptions.py` — собственные исключения.

**Главный вопрос:** какие базовые механизмы нужны приложению для работы?

Core не должен содержать конкретную бизнес-логику.

---

## 3. Models — модели данных

`models/` содержит описание структуры данных, которые хранятся в базе данных.

При использовании SQLAlchemy здесь располагаются ORM-модели.

Например, модель StorageEvent может содержать:
- `id` — идентификатор события.
- `event_type` — тип события.
- `user_id` — идентификатор пользователя.
- `bucket` — имя бакета.
- `object_name` — имя объекта.
- `timestamp` — время события.

Модель описывает структуру данных и связи между таблицами.

Она не должна самостоятельно выполнять анализ или обращаться к MinIO.

**Главный вопрос:** как устроены данные?

Важно: ORM-модели SQLAlchemy и Pydantic-схемы — разные вещи. Первые описывают хранение данных, вторые — формат и валидацию данных.

---

## 4. Repo — Repository

`repo/` — слой доступа к данным.

Репозитории отвечают за получение, сохранение, изменение и удаление данных.

Например, `EventRepository` может содержать методы:

- `create()` — создание записи.
- `get_by_id()` — получение записи по ID.
- `get_recent()` — получение последних событий.
- `get_by_period()` — получение событий за определённый период.

Репозиторий работает с базой данных, но не принимает бизнес-решений.

**Главный вопрос:** как получить или сохранить данные?

---

## 5. Services — бизнес-логика

`services/` содержит прикладную логику приложения.

Сервисы организуют выполнение операций и взаимодействуют с другими компонентами.

Например, `EventCollectorService`:

1. Получает информацию об операции.
2. Определяет тип события.
3. Подготавливает данные.
4. Передаёт их в `EventRepository`.
5. Сохраняет событие.

Другой пример — `AnalyticsService`:

1. Получает события через репозиторий.
2. Передаёт данные анализатору.
3. Получает результаты анализа.
4. Сохраняет результаты.

**Главный вопрос:** что приложение должно сделать и в каком порядке?

---

## 6. Взаимодействие компонентов

Пример получения последних 100 событий:

    HTTP Request
         |
         v
        API
         |
         v
      Service
         |
         v
      Repository
         |
         v
      PostgreSQL

Ответ возвращается обратно по той же цепочке.

- API принимает запрос и возвращает HTTP-ответ.
- Service организует выполнение операции.
- Repository получает данные из БД.
- Model описывает структуру записи.

    S3Analyzer/
    ├── core/
    │   ├── config.py
    │   ├── database.py
    │   └── logging.py
    │
    ├── models/
    │   └── storage_event.py
    │
    ├── repo/
    │   └── event_repository.py
    │
    ├── services/
    │   ├── event_collector.py
    │   └── analytics_service.py

    ├── api/
    │   ├── events.py
    │   └── analytics.py
    │
    └── main.py

Это пример, а не обязательный стандарт. По мере роста проекта могут появиться дополнительные директории.

---

## 8. Основные правила архитектуры

1. Один модуль — одна основная ответственность.
2. Не размещать SQL-запросы непосредственно в API.
3. Не помещать бизнес-логику в ORM-модели.
4. Не заставлять Repository принимать бизнес-решения.
5. Не создавать дополнительные слои без необходимости.
6. Разделять сбор данных и их анализ.
7. Делать компоненты удобными для независимого тестирования.

---

## 9. Модульный монолит и микросервисы

**Модульный монолит** — одно приложение, разделённое на логические модули. Они используют общую инфраструктуру и могут взаимодействовать напрямую.

**Микросервисы** — несколько независимо развёртываемых приложений или процессов, взаимодействующих через API, брокеры сообщений и другие определённые интерфейсы.

Важно: разделение проекта на директории `core`, `services`, `repo` само по себе не делает его микросервисным.

Для начала разработки S3 Analyzer рекомендуется модульный монолит с возможностью последующего выделения отдельных фоновых процессов.

---

## 10. Краткая шпаргалка

- `core` — на чём работает приложение.
- `models` — какие данные существуют.
- `repo` — как работать с данными.
- `services` — что приложение делает.
- `api` — как пользователь взаимодействует с приложением.
- `analyzers` — как интерпретируются собранные данные.
- `workers` — какие фоновые задачи выполняются.
